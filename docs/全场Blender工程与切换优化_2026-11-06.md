## 可编辑工程

文件：`art/whole-scene/poolrooms-master.blend`。

- `00 / CONNECTED - seven zones + hall`：七区、静水扩展、剧情浅水廊和日光厅。七区采用目前运行的 Blender 烘焙建筑与道具几何，保留实际细节，没有退回早期程序方盒。日光厅按转场坐标旋转 180°，平移到 `(21.25, 0.24, 39.5)`，与漫游区实际门口相接。
- `01 / ARCADE`：剧情拱廊、连通闸及其连接管道。
- `02 / SHAFT`：深井、水下设施、楼梯、观察窗及交互布置。
- `03 / MEMORY`：回忆阶段。与深井保持各自独立场景，不把叙事状态堆成多层楼。

每区分为 Architecture、Furnishings、Water references、Interaction anchors、Lights and cameras。原始 GLB 的倒角法线、UV、表面类型保留；同一光滑面内的共点已焊接，硬边继续分开。米制 SurfaceUV 与原始 RuntimeUV0/1 分开存放，便于改材质而不破坏烘焙坐标。颜色、法线、粗糙度和共用天空图片已打包进 blend。

产物包含 5,635 个对象、812,926 个三角面、28 张打包图片，文件约 40 MB。水面采用游戏实际的分区网格，包含各自水位与台阶裁切，避免用重叠矩形替代；另补齐七区光井封闭面，并通过 Blender 网格验证器清理退化面。此数字是编辑工程总量，包含各剧情状态及水面参照，不是游戏同时绘制的数量。准确清单见 `art/whole-scene/manifest.json`。

重要边界：这是完整的建模母版，并非已经重新烘焙、替换全部运行时资产的新版本。水面在 Blender 内使用 IOR 1.333 的透射材质作为建模预览；实时折射、焦散、脚步扰动、碰撞、水闸、磁带、音频和 UI 继续由应用实现。Canvas 生成的文字保留牌子实体和交互标签，未转为 Blender 字体对象。不要把参考水面导出后覆盖实时水材质。

## 已修改的运行时卡顿来源

1. **房间反射探针。** 之前 CubeCamera.update 在同一帧绘制六个方向，再生成 PMREM。现在每帧只捕获一个方向，第七帧才过滤并发布完整探针；未完成时继续使用上次有效反射。
2. **剧情照明初始化。** 三张 EXR 探针改为逐帧生成；同一 renderer 内保留 90 秒的照明缓存，快速往返无需全部重做。没有把整个场景及水面大缓冲永久保留在显存里。
3. **纹理、几何与程序首次使用。** 新增 `gpuWarmup.ts`，在加载页下逐张上传纹理、分批用小尺寸无副作用代理上传真实几何/实例缓冲，再分批调用 compileAsync。代理不会触发水面与 Reflector 的递归捕获，也不调用 Reflector.clone 建立多余渲染目标。
4. **首进重复创建。** 初次点击“走进去”现在复用已经加载的同幕场景；从存档进入其他幕或游戏结束后重新开始仍按实际状态切换。
5. **下一幕准备。** 在接近出口时准备下一幕，并上传、编译其资源；需要等待时停留在遮蔽的连接段，仍接受环顾输入，避免抵达出口才集中编译。
6. **换幕额外截图。** 观察窗的旧厅图像提前准备，并隐藏所有水面，避免为一张小图又触发嵌套水体捕获。换幕边界直接使用准备好的图像。

没有降低主场景分辨率、抗锯齿规格或池水捕获分辨率来换取这次优化。首次冷启动仍有资源上传和编译成本，只是纳入主题加载页并分散执行；大型 JS 包与 HDR 体积仍需后续优化。

## 验证与限制

运行 `npm run build` 检查 TypeScript、Vite 主入口和离线剧情构建。构建保留已有的大体积 JS 警告。

定点检查脚本 `.work-backup/check-scene-warmup.cjs` 使用独立资料目录、隐藏 Electron 窗口和本地 HTTP 服务，不操作用户游戏窗口。检查七区加载、浅水廊加载、首次开始的场景身份、下一幕预热完成及切换时是否消费同一准备对象。结果为 `.work-backup/scene-warmup-check.json`。它通过本地调试入口推进一次管道转场，不等价于完整手动通关，也不是前台 FPS 基准。

检查中发现边界仍有额外绘制：一次冷缓存换幕约 394 ms，随后分段检查约 39.3 ms，其中 33.5 ms 在额外渲染、约 0.9 ms 在释放旧房间。因此继续移除了边界上的嵌套捕获，而不是仅调整场景销毁策略。最终数字以最后一份检查结果为准，不把不同缓存状态的两次数字视作严格性能 A/B。

最终定点结果：七区与浅水廊均退出加载页、WebGL 有效、缓冲为 1920 × 1203；首次开始复用原场景；下一幕分帧预热约 2.01 秒并被换幕复用。换幕 CPU 约 **5.1 ms**，其中旧房间释放约 **0.8 ms**，边界额外 render 调用为 **0**。控制台 error 为空，只有开发检查窗口的 Electron CSP 提示。本次已有驱动/文件缓存，启动时间约 5.65/13.33 秒不能作为冷启动保证；5.1 ms 也不包括随后一帧的 GPU 完整绘制。

Blender 总工程已重新打开并渲染一次导入预览。`master-preview.png` 是 Blender 建模检查图，不能作为游戏画质达标的证据。用户截图中的天窗底部黑边、曲墙突变高光、水线亮边和强白窗反射仍属于待处理的几何/烘焙/反射一致性问题，本轮不标记全部修复或稳定 60 FPS。

## 继续建模与回传

1. 直接打开总工程，选择对应 Scene，再按集合编辑建筑、台阶、池岸、光井。修改后的版本另存，避免重新运行生成器覆盖手工编辑。
2. 改动门口、台阶或池底后，同步 `layout`、`rooms.ts`、`quietBath.json` 等导航/水深数据；保留交互锚点 ID。
3. 只重烘焙、导出受到改动的分区，保留世界米制 UV、光照坐标及表面元数据，逐区接回现有加载流程。不要导出一个全世界单网格，避免失去剔除、实例化和流式加载能力。
4. 生成母版的可复现入口：`node scripts/export-whole-scene.mjs`，再执行 `node scripts/blender.mjs run scripts/build-whole-scene.py`。生成过程从当前运行几何读取，不修改冻结参考。
