## 2. 池核是什么：外部流派结论

### 2.1 术语与谱系

Poolcore / Poolrooms / Liminal Pool 没有权威统一定义。最稳妥的理解是：**Liminal Space 是上位概念；Poolcore 是以白瓷砖、蓝绿水面、水光折射、空无一人、超出功能的尺度为核心的视觉子类；Poolrooms 是它最常见的场景化称呼；Dreamcore 是更宽的美学近亲。**

时间线：2020 年 Jared Pike 的 Dream Pools 定型视觉语言 → 2022 年被 Backrooms 社区吸收为 Level 37「Sublimity」→ 2024 年 Tensori 的 POOLS 完成游戏化 → 2025 年 Dreamcore 产品化 → 2026 年电影、VR 与大量同质作品把池核推向主流，也推向过剩。

### 2.2 有效公式

- **构图先于建模**：24–35 mm 等效、眼/腰高机位；先定 7–9 个“一区一镜头”，再决定墙、柱、门洞。
- **强日光 + 可读暗部**：受光竖直面成为白色体块，背光面保留灰绿层次，深处进入黑暗；不要靠均匀补光或自发光救暗部。
- **硬瓷砖 vs 有机水面**：瓷砖过于完好、统一、洁净；水面必须有真实反射/折射/波纹。两者对比是池核的质感来源。
- **遮挡与路径**：前景粗柱/拱只能露出局部空间；每个转角都要承担视线变化或路线变化。
- **声音是第二空间**：脚步、滴水、水拍岸、回声随房间变化；POOLS 把“环境本身是怪物、无怪物”当作卖点。
- **少即是多**：池核不是靠房间数量或资产密度成立；一个可读的暗部、一个异常尺度，比十个复制房间更有效。

### 2.3 玩家最常批评什么

来自 POOLS / Dreamcore 的 Steam 差评与评测：

- **迷宫变瞎转**：没有地标、没有回路、没有可读方向。
- **留白过头**：空间很大但没事发生、没有可交互对象，玩家会觉得“没做完”。
- **内容量不足**：2 小时/几张图卖全价，和免费 VRChat 地图比较。
- **恐怖元素破坏氛围**：后期出现人偶、影子人、突脸音效，与“无怪物”承诺矛盾。
- **章节化/加载破坏沉浸**：过场黑屏把“迷路感”打断。
- **同质化**：2026 年 Steam 上已有大量白瓷砖 + 水 + 暗角的近似作品，仅靠视觉母题不足以被记住。

### 2.4 对 AUREOLE 的启示

AUREOLE 与纯走路模拟不同：它有三幕、阀门、水位、磁带、存档和巡检 UI。这是差异化，但也意味着它不能只靠氛围；**必须把“水位”做成真正的空间动词，把“磁带”做成信息闭环，否则会落进 Dreamcore 式“好看但没事做”的差评区**。同时不要加怪物/jump scare，不要在探索段加常驻 HUD 或任务清单；这两条是池核口碑的高压线。

## 4. 实机诊断：当前“白模”的根因与证据

### 4.1 P0：`AtlasMaterial` 丢失 albedo、重复叠加 GI

代码位置：

```glsl
// src/world/AtlasMaterial.ts:31-34
vec3 albedo = finish < 0. ? vec3(.74,.79,.80) : tex.color;
diffuseColor.rgb = atlasLight;   // ← 这里覆盖了 albedo
```

```glsl
// src/world/AtlasMaterial.ts:52-53
irradiance += atlasLight * atlasGain;
```

`atlasGI` 的烘焙方法是 “Cycles indirect + occluded sky direct; **no albedo or direct sun**”（`art/map-atlas/roam/bake-report.json`）。所以 `atlasLight` 只是光照，不是颜色；把它当 `diffuseColor` 会得到没有材质颜色的“白模”，同时 `irradiance += atlasLight * gain` 再把同一份 GI 加一次，造成亮部平方级放大、暗部直接归零。

**验证**：Lead 在运行时（不改源码）把该行替换为 `diffuseColor.rgb = albedo;`，同一机位截图：

- `hall-pool-before.png` → `hall-pool-after.png`：白瓷砖缝、蓝马赛克池底、池沿材质恢复；平均亮度 186.6 → 166.5，p99 高光从 255 → 207。
- `hall-bath-before.png` → `hall-bath-after.png`：从一片灰白墙变成有砖缝的白瓷砖墙和蓝色马赛克池底。
- `hall-daylight-before.png` → `hall-daylight-after.png`：立柱和墙面出现砖缝，亮部不再整片削顶。

证据目录：`.work-backup/lead-probe/`（全部 before/after 与 `probe-report.json`）。

**影响**：这是当前“不可展示”的第一硬伤。修这一处预计同时缓解“墙面发白、池底无颜色、暗部死黑”三项 50% 以上的问题；后续还需重新调曝光/太阳强度/Bloom。

### 4.3 P1：剧情首屏约 18 秒

实测同一台机器、1440×900、Electron 离屏：

- `index.html` 到区域按钮可交互：2.4–5.1 s（Vite 首次编译）。

## 5. 代码与数据风险

以下只列对玩家有直接影响、且本次有代码证据的条目；完整清单见 code-auditor 报告。

### 5.1 确认的 bug

**B1 结束清档会被 `pause('end')` 重新写回**（`Inspection.ts:806`、`257-263`、`895`）

`localStorage.removeItem(checkpoint)` 后立即 `this.pause('end')`，而 `pause()` 首行是 `this.save()`；`save()` 只排除 memory/preview/isolated/demo，没有排除 `page==='end'`。所以通关后清掉的存档又在同一帧被写回，`dispose()` 还会再保存一次。修复：给 `pause(page, save=true)` 或 `saveSuppressed` 参数，结束页不保存；`dispose()` 同样跳过。

**B2 `?preview=link` 演示仍会读取用户 checkpoint**（`Inspection.ts:233-241`）

`start(resume)` 只判断 `resume && !this.preview`，没有判断 `this.link?.demo`；`save()` 虽然排除了 demo，但读取没有排除。触发后演示会跳到用户存档幕。修复：`if(resume && !this.preview && !this.link?.demo)`，`hasSave()` 在 demo 下返回 false。

**B3 `RoomReflections` 实际是 no-op**（`RoomReflections.tsx:33-37`）

它只处理 `material.userData.reflectionRoom !== undefined` 的 `MeshStandardMaterial`；唯一写入点是 `fixtureMaterials.ts:52-53`，而 `createFixtureMaterials` 只在不可达旧模块中被调用。`prepareAtlas` 的材质没有 `reflectionRoom`，所以进入任意 roam 后 `byRoom` 为空、直接 return。房间级 cubemap/PMREM 反射并不存在。

**B4 `WindowLightShafts` 永远为空**（`liminalLayout.ts:28`、`LiminalAtmosphere.tsx:52-65`）

`windows: Opening[] = []`，`WindowLightShafts` 遍历零次；如果按新版 `roamPlan.wells` 本应有采光井光束，这是视觉回归；如果刻意移除，应删掉组件，避免误判。

**B5 `WaterCaustics` 完整 GPU 子系统无人消费**

`DreamPoolScene.tsx:107` 调 `useWaterCaustics`，`LiminalArchitecture.tsx:19` 忽略 `caustics` prop，`PoolWater.tsx` 的 `uCaustics` 在 `waterOptics.ts` 中只声明未使用；真正采样的 `liminalMaterials.ts` 不可达。`WaterCaustics.ts:17-18` 分配 1536² HalfFloat（约 18.9 MB）并以 20/15/10 Hz 渲染，但画面不显示，纯浪费 GPU/显存。

### 5.2 潜在风险（发布前应核实）

- **拱门边缘碰撞**：`allowed()` 只做矩形/足底判定，`move()` 仅用 `ceilingAt` 钳制脚高；贴拱边可能穿模/镜头下沉（`Inspection.ts:526-536`、`600-601`）。
- **旧 `quietBath.json` 仍在运行时被 shader 引用**：`rooms.ts:11-12`、`ceramic.ts:4`、`TileShader.ts:46-56`；旧 lightWells/arcWalls/bounds 与新 `hallPlan` 可能漂移，形成局部亮斑/砖缝接缝。
- **StoryWater 每个水盆约 30 MB 显存**：survey/refraction/mirror/interior target；hall 两盆约 60 MB；静态站立仍约每 0.16 s 重渲染 mirror（`StoryWater.ts:99-104`）。
- **PoolWater 移动时 30 Hz 全场景双 pass**：高画质 refraction 2560/368 万像素 + mirror 1536/118 万像素（`PoolWater.tsx:86-89,119-121,132-155`）。
- **`prepareAtlas` 克隆 GLB 几何不共享 GPU buffer**：切幕时同步构造，`gpuWarmup` 只藏编译不藏 CPU 构建；读档到 arcade/shaft 可能卡首帧。
- **GLB 与 mapPlan 没有自动一致性校验**：`check-map-atlas.mjs` 只检查逻辑 plan，不检查 GLB bounds/池体/UV；Blender 重导出后可能水面悬空/门洞错位。
- **无测试文件、无 lint/test 脚本**：只有 `build` 与两个 Electron 检查脚本；`Inspection` 存档/清档/页面转换没有单元测试。

### 5.3 代码气味

- `Inspection.ts` 907 行、30+ 私有字段，输入/移动/存档/动画/场景切换全部耦合。
- 约 24 个 `src` 文件在入口可达图中不可达（旧 `Architecture.tsx`、`SampleArchitecture.tsx`、`blenderAssets.ts`、`poolDetails.ts`、`roomFixtures.ts`、`bakedBathLighting.ts` 等）。
- `buildMap/solidSurface` 仍保留旧程序化几何链（Node 基准约 227 ms、247 万 cell），当前 GLB 路径不调用。
- `build-story.mjs:20-22` 在已有 `>` 的 `<link>` 后追加 `>`，生成 `...css">>` 非法 HTML（浏览器容错）。
- 离线包 20 MB、主 JS 1.64 MB gzip 538 kB，缺少按幕分包。

## 6. 设计层面的关键判断

### 6.1 现在最可能“不好玩/不好看/不好懂”的环节

1. **不好懂：开局没有目标且朝向错误。** `entryPose()` 把玩家放在 [-0.6,0,28.6]，却 `lookAt(-8.6,1.2,28.25)`，正对西侧 bath-entry，而不是北侧 28 m 日光厅。`starts.hall`（“总闸是关的。”）只在 `switchAct` 的非 hall 分支播放；首次 `start()` 因 `next===this.act` 走 `resetLevels/entryPose` 分支，不播这句（`Inspection.ts:25,113-117,193-197,244-247`）。玩家第一眼看到小浴池且不知道该干什么。
2. **不好玩：水位退化成门禁开关。** 全剧只有 4 类阀门交互；第二幕两个开关就是二值联动；没有“淹掉一条路打开另一条路”，没有“水追人”，没有“水位改变尺度”。玩家大部分时间在走路和按 E。
3. **不好看：白模 + 4 个贴墙机位 + 水面接缝。** 参考 §4。
4. **不好懂：磁带链无法自证“建筑即症状”。** 真正必看只有 #01/#03；#00 藏在三次回环后；第三层、多两跨、观察窗、遮阳布都没有空间证据，玩家听完 #00 的“我们从来没有往下铺过第三层的瓷砖”后无法在场景中找到对应物，会把留白读成没做完。
5. **不好玩：七区是无玩法的观景器。** 24 个房间只有体力、水深、区域名和滑梯提示；没有阀门、磁带、目标。默认入口 `/` 很容易让玩家把项目当成“池核观景器”，而真正有谜题的三幕藏在 `/story.html`。

### 6.2 最值得做的 5 件事

1. **先修主池/日光厅的视觉样板。** 修 `AtlasMaterial.ts:34` → `diffuseColor.rgb=albedo;`，重新构建并用同一机位、FOV、太阳角度重截 13 张图；然后调曝光/太阳强度/Bloom，直到亮部、灰部、暗部和水下砖缝同时可读。没有这个样板，继续加房间只会放大问题。
2. **把水位做成真正的核心动词。** 每幕至少 3 个可读水位状态（或联动水体），让同一空间在不同水位下出现“新路打开/旧路被淹”的双向变化；用物理水位尺、漂浮物、水痕和声音表达当前水位；第二幕做一次真正的“水追人”段落，终局涨水保留为第二次。
3. **重建无 HUD 的引导链。** 修正出生朝向，第一眼看向 28 m 日光厅；把排水阀/供水闸/主涡轮做成建筑上可读的“磨亮、手印、黄铜发亮”；把水位尺做成真的可读刻度；恢复一个可辨认的 60Hz 泵声信标（或等效低频方向声）。
4. **把主线压回 10–15 分钟的三箱节奏。** 以设计 §6.0 三箱 4–5 分钟为标准，把剧情 18 个房间合并/删减到 12–14 个有功能的房间；七区 24 房间要么降级为明确的自由漫游模式，要么收掉。范围不砍，水位/叙事/视觉都做不深。
5. **修复两条体验链：深水三上三下 + 磁带信息闭环。** 深水段补足 3 个气穴（当前只有 `(-7,-4)` 一个）、加入呼吸/心跳反馈、让三块铭牌的“手电侧照”稳定可读、主涡轮有真实吸力/阻力反馈；磁带保证 #01/#03 必看、#02/#00 可选但可发现，并在 #00 后给一个空间级回望 payoff（第一幕封死观察窗 ↔ 第三幕看到第一幕池底）。

### 6.3 最不该做的 3 件事

1. **不要继续加房间、楼层、新场景或第二套地图。** 42 个房间/13 个水盆已经在稀释体验；下一步是删减和深化，不是扩大 `mapPlan.ts`。
2. **不要用更多 HUD、字幕、任务列表、目标标记来救“不好懂”。** 池核的安静与留白是核心资产；正确做法是把信息放回世界（水位尺、门缝光、水渍、泵声、阀门磨损）。
3. **不要在单间视觉样板和完整新玩家通关之前，继续烤全图、追全图 60 FPS 或扩展新渲染管线。** 当前 8.44 MiB GLB、107 万三角形、20 MB 离线包的优化投入，若视觉方向未锁定，很可能是在错误目标上做工程。

## 8. 最后判断

这是一个 **“基础设施完成度远高于体验完成度”** 的版本。数据一致性、Blender 资产管线、场景切换、存档版本、磁带播放和深水交互证明团队已经做出了完整的可运行骨架；`geometry-check`、`review.json` 和 `route-check` 也证明骨架不是纸上方案。

但池核的价值不在房间数量和三角形数量，而在玩家能否在一个可读的、安静的空间里，用水位、磁带和建筑异常自己拼出意义。当前版本最缺的不是更多内容，而是：

1. **一个视觉上站得住的主池样板**（先修 albedo，再调曝光/材质）；
2. **一条玩家能自己读懂的 15 分钟主线**（修出生朝向、砍房间、升级水位）；
3. **一次真实新玩家验收**（不是控制器快进，也不是后台截图）。

在这三件事完成前，建议所有“已完成”表述都保留限定词：**可运行、可构建、几何可达，不等于体验成立。**
